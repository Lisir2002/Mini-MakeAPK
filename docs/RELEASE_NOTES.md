# 发版日志与 Release 页面规范（Release Notes）

> 状态：已生效（2026-10-25）· 受 `docs/DOC_CHARTER.md` 约束
> 本文件是**发版日志写法与 Release 页面格式的唯一事实来源**，借鉴 MiniMe-core 发版规范并结合 MMA 版本规则（[`VERSIONING.md`](VERSIONING.md)）适配而成。
> 结构目录见 [`Version Log/README.md`](Version Log/README.md)。

---

## 1. 适用范围与三处一致

发版说明存在于三个载体，**内容必须逐字一致**（Release 正文去掉版本标题行）：

| 载体 | 位置 |
|------|------|
| 汇总日志 | `docs/Version Log/CHANGELOG.md` 的版本条目 |
| 独立版本文档 | `docs/Version Log/MMA v-Logs/MMA {版本号} Version Log.md` |
| GitHub Release | Release 标题与正文 |

**本规约为发版最高优先级约束之一。任何违反即视为发版未完成，必须修正。**

---

## 2. 命名规范

| 对象 | 格式 | 示例 |
|------|------|------|
| 发布 tag | `v{版本号}` | `v0.0.0.1-rc1`、`v0.0.0.1` |
| Release 标题 | `MMA {版本号} — {更新内容概括}` | `MMA v0.0.0.1-rc1 — 界面图标矢量重绘与安装包瘦身三成` |
| 安装包 | `MMA-v{版本号}-{变体}.apk` | `MMA-v0.0.0.1-rc1.apk`、`MMA-v0.0.0.1-release.apk` |
| 独立版本文档 | `MMA {版本号} Version Log.md` | `MMA 0.0.0.1-rc1 Version Log.md` |

- **标题概括**：≤20 字，用**用户语言**描述本次最核心的 1～2 个变化，禁止内部术语。
- **变体**：`rcN`（预览版）/ `release`（正式版），CI 按 tag 是否含 `-rc` 自动判定。
- 反例：`v0.0.0.1`（无概括）、`Release v0.0.0.1`（无意义前缀）、`feat: vector icons`（开发语言）。

## 3. 发版说明格式（用户面向 · 唯一规约 · 硬性约束）

**严格结构（按此顺序，无内容的分类省略）：**

```markdown
> {100字以内简介：一句话说清本次更新的核心价值，用户语言，无内部术语}

### 新功能
- **{4-9字小标题}**：{20-40字简练说明，描述用户可感知的新增功能}。

### 改进
- **{4-9字小标题}**：{20-40字简练说明，描述体验优化、性能提升、样式调整等}。

### 移除
- **{4-9字小标题}**：{20-40字简练说明，描述被删除、弃用或不再支持的功能}。

### 修复
- **{4-9字小标题}**：{20-40字简练说明，描述修复的问题及症状}。

### 安全
- **{4-9字小标题}**：{20-40字简练说明，描述安全相关改进}。

### 已知问题
- **{4-9字小标题}**：{20-40字简练说明，描述已知但未修复的问题；无则写「无」}。
```

**条目格式铁律（逐条核对，违反即重写）：**

1. **小标题**：4-9 个汉字，加粗，准确概括条目核心，不得使用「功能优化」「多项改进」等泛化表述。
2. **分隔符**：小标题后接全角冒号（`：`），再接说明句。
3. **说明句**：20-40 字，描述变化之处而非代码实现，以句号结尾。
4. **分类顺序**：新功能 → 改进 → 移除 → 修复 → 安全 → 已知问题，不得调换。
5. **禁止安装包链接**：Release 正文不写下载链接，GitHub 自动展示 Assets。
6. **禁止完整更新历史链接**：GitHub 自动展示 compare 链接。

## 4. 禁止 emoji（强制约束）

**所有发版相关内容一律禁止使用表情符号，保持纯文字、简洁专业。**

| 载体 | 禁止内容 |
|------|----------|
| Release 标题 / 正文 | 分类标题、条目正文、已知问题标注均不得使用 emoji |
| CHANGELOG.md / 独立版本文档 | 版本标题、分类标题、条目正文均不得使用 emoji |
| 安装包文件名 | 不得出现 emoji |
| 校验脚本输出 | 不得包含 emoji |

- 分类标题统一纯文字：`新功能` / `改进` / `移除` / `修复` / `安全` / `已知问题`。
- 破坏性变更和已知问题用「注意」或「重要」等纯文字标注，不得用 ⚠。
- 正例/反例标注用「正例：」「反例：」纯文字。

## 5. 写作铁律（逐条核对，违反即重写）

1. **利益优先**：每条先说「用户能做什么」，不说「我们做了什么」。正例："你可以独立调节每个模型的温度"；反例："新增模型级 temperature 覆盖"。
2. **平实语言**：禁止内部术语、类名、函数名、表名、ticket 号、commit hash、migration 编号。
3. **每条一个变更**：禁止「各种改进」「多项优化」「修复若干问题」等模糊表述。
4. **小标题+说明句**：每条必须为「**4-9字小标题**：20-40字说明」结构。
5. **描述症状而非代码**：修复项写用户遇到的问题，不写技术根因。正例："修复了删除记录后历史页偶发闪退"；反例："修复 deleteById 未级联清理 build_steps 导致 NPE"。
6. **最新优先**：版本倒序排列，最新版本在最上方。
7. **破坏性变更醒目标注**：用「注意」开头，并明确说明用户需要做什么操作。
8. **简介≤100字**：一句话说清核心价值，不罗列功能清单。
9. **仅记录应用程序变更（绝对禁止项）**：版本日志只记录用户可感知的应用程序功能、体验、性能、安全变更。**绝对禁止**出现以下内容：
   - 纯文档变更（README、规范文档、发版说明本身的更新）
   - 纯项目配置变更（CI 工作流调整、构建脚本修改、lint 配置，除非直接影响用户体验）
   - 项目管理变更（目录结构调整、文件重命名、仓库维护操作）
   - 纯代码重构（无用户可感知变化的内部重构）
   - 依赖版本升级（除非修复了用户可感知的问题或新增了能力）
   - 发版流程、规范约束、格式调整等元变更
   - 以上变更若确需记录，仅在「改进」分类中以用户可感知的结果描述，不得提及内部实现。
   - **关键词自检（发版前强制）**：生成后逐条扫描，不得出现「文档」「docs/」「规范文档」「README」「CHANGELOG」「CI」「workflow」「构建脚本」「versionCode」等元变更关键词。
10. **内部重构笼统描述（强制约束）**：品牌名遗留清理、代码架构重构、内部模块合并等用户不可见的技术变更，若发版周期内确需记录，**必须**使用笼统描述，不得出现具体类名、文件名、函数名、技术术语。标准表述模板：
    - **架构细节优化**：应用架构细节优化，提高产品质量，优化用户体验。
    - **代码质量提升**：内部代码质量持续提升，增强稳定性与可维护性。
    - **项目结构优化**：项目结构优化整理，提升长期可维护性。
11. **用户可感知边界判定（强制约束）**：只记录用户可直接感知的结果，不记录实现手段：

    | 内容类型 | 用户可感知？ | 处理方式 |
    |----------|-------------|----------|
    | CI门禁、静态检查、lint 规则、代码扫描 | 否 | 禁止写入，或仅以"稳定性提升"笼统描述结果 |
    | 单元测试覆盖率提升、测试用例新增 | 否 | 禁止写入 |
    | 构建速度提升、编译优化、CI 流程优化 | 否（仅开发者感知） | 禁止写入 |
    | 代码重构、架构优化、模块合并 | 否 | 按第 10 条笼统描述 |
    | 崩溃率降低、闪退修复 | 是（间接感知） | 可写"稳定性提升"或具体修复症状 |
    | 启动速度变快、操作更流畅、响应更迅速 | 是（直接感知） | 可写具体体验改善 |
    | 安装包体积减小、下载安装更快 | 是（直接感知） | 可写具体数据 |
    | 安全加固、漏洞修复、隐私保护增强 | 是（间接感知） | 可写安全相关改进，不写技术细节 |

    **手段与结果分离原则**：若一条变更同时包含技术手段和用户结果，只保留结果部分。
    - 反例：「代码压缩：启用 R8 与资源压缩，重写 proguard 规则」（手段）
    - 正例：「安装包瘦身：安装包体积由约 36MB 降至约 25MB，下载与安装速度明显加快」（结果）

## 6. 发版流程

```
① 本地验证 ── testDebugUnitTest + verifyPaparazziDebug 全绿
      │
② 确认授权状态 ── 已获用户授权 → 正式版；未授权 → RC（见 VERSIONING.md §3）
      │
③ 更新 CHANGELOG.md ── 新增版本条目（本规约格式；[Unreleased] 为暂存区，发版时晋级）
      │
④ 创建独立版本文档 ── MMA v-Logs/MMA {版本号} Version Log.md（内容与条目一致）
      │
⑤ 提交推送到 main ── 发版相关脚本与规范的最新改动必须已在 main
      │
⑥ 打 tag 并推送 ── v{版本号}（CI 强校验：tag⇔versionName、CHANGELOG 有条目、
      │                versionCode 单调、证书指纹、APK 命名）
      │
⑦ CI 产出成品 ── 校验 → 测试 → 签名构建 → 按规范命名 → 创建 Release 上传
      │
⑧ 人工完善 Release 页面 ── 标题补 ≤20 字概括（MMA {版本号} — {概括}），
      │                        正文与 CHANGELOG 条目一致（CI 已预填正文）
      │
⑨ 格式校验 ── python3 scripts/gitops/check-release-format.py --tag {tag}
      │
⑩ 校验通过（退出码 0）── 发版完成
```

## 7. 发版完成 Checklist（强制 · 逐项核对）

> **发版"完成"的唯一定义：以下所有项全部通过。**

**发版前（打 tag 前）：**
- [ ] 本地 `testDebugUnitTest` + `verifyPaparazziDebug` 全绿
- [ ] 授权状态已确认（正式版有用户授权；未授权则版本号带 `-rcN`）
- [ ] `CHANGELOG.md` 已新增版本条目，符合本规约格式
- [ ] 独立版本文档已创建，内容与 CHANGELOG 条目一致
- [ ] 条目通过关键词自检（无文档/CI/workflow 等元变更词）
- [ ] `versionCode` 已 +1 且大于历史所有值

**发版后（CI 构建成功后）：**
- [ ] CI 构建成功，APK 已上传 Release Assets，命名符合 `MMA-v{版本}-{变体}.apk`
- [ ] APK 签名校验通过（CI 证书指纹门禁绿）
- [ ] Release 标题符合 `MMA {版本号} — {更新概括}`（概括 ≤20 字）
- [ ] Release 正文已从 CHANGELOG 条目生成，无占位符残留
- [ ] 正文条目格式合规：每条为 `**4-9字小标题**：20-40字说明`
- [ ] 正文无 emoji、无内部技术术语
- [ ] 正文仅记录用户可感知的应用程序变更
- [ ] 三处载体内容一致：Release 正文 = CHANGELOG 条目 = 独立版本文档
- [ ] `python3 scripts/gitops/check-release-format.py --tag {tag}` 校验通过（退出码 0）

## 8. 格式校验工具

```bash
# 校验指定版本
python3 scripts/gitops/check-release-format.py --tag v0.0.0.1-rc1

# 校验最新正式版本
python3 scripts/gitops/check-release-format.py --latest
```

**校验项：**
1. 标题格式（软件名 + 版本号 + ≤20 字概括）
2. 正文无占位符（请补充、请提炼）
3. 条目格式（4-9 字小标题 + 20-40 字说明）
4. 无 emoji
5. 无内部技术术语（关键词表）
6. 分类正确（新功能/改进/移除/修复/安全/已知问题）
7. 三处载体一致（Release 正文 = CHANGELOG 条目 = 独立版本文档）

**CI 门禁分工**：CI 在创建 Release 前执行硬校验（CHANGELOG 有条目、正文非空、无 emoji、无占位符），完整格式校验（字数、三处一致）由发版后脚本负责。
