# MMA / Mini-MakeAPK · UI 设计审计报告

> 审计人：颜好看（Yan，UI/UX 设计师）
> 日期：2026-10-28
> 范围：现有设计语言 `DESIGN_LANGUAGE.md` + Compose 主题层（`ui/theme/*`）+ 顶/底栏组件（`MmaTopBar.kt` / `MmaBottomBar.kt`）
> 目标：对照用户 4 项硬需求，给出「现状 vs 目标」诊断，并产出可落地的设计令牌与视觉方向。
> 约定：本次**只做审计 + 设计产物 + 预览**，不修改任何 Compose 代码（详见结尾「落地建议」）。

---

## 0. 一句话结论

用户要的是「**黑白为主、蓝点缀、顶底栏瘦身、文字适中、令牌全覆盖**」的干净专业界面；而现有设计语言是「**珊瑚粉单色 + 大圆角 + 可爱 iOS 风**」，**方向根本冲突**——必须整体换色板并补齐令牌，而非打补丁。本审计给出冲突清单与锁定令牌（`docs/design/tokens/design-tokens.json`），供架构师与工程师对齐实施。

## 1. 逐条需求诊断

### 需求 1 · 顶栏、底栏不要太宽（瘦身）

| 项目 | 现状 | 目标 | 证据 | 诊断 |
|---|---|---|---|---|
| **顶栏高度** | `heightIn(min = 56.dp)` | **52dp**（最小） | `app/.../components/MmaTopBar.kt:58` `.heightIn(min = 56.dp)` | 偏厚 4dp；且写死 56，无令牌化。门禁 `check_token_usage.py:56` 把 56 列为「顶栏规范高度」，但用户已锁定 52，需同步下调并令牌化。 |
| **底栏高度** | 用 M3 `NavigationBar`，**未设任何高度** | **56dp** | `app/.../components/MmaBottomBar.kt:57` `NavigationBar(` 无 modifier 高度；`check_token_usage.py:47-60` 的 `COMPONENT_SIZES` 仅列 56（顶栏）**未列 80** | **头号厚度问题**：M3 `NavigationBar` 默认高度 **80dp**，当前无任何覆盖 → 底栏比目标厚 24dp（约 43%）。这是「底栏太宽/太厚」的直接根因。 |

**结论**：顶栏需从 56→52dp；底栏必须显式设 56dp（覆盖 M3 默认 80dp）。两者都应令牌化为 `topBarHeight` / `bottomBarHeight`（见 `design-tokens.json → chrome`）。[注意] 注意：门禁当前允许集未含 52/80，工程师落地时需在 `check_token_usage.py` 的 `COMPONENT_SIZES` 增 `52`（顶栏）并显式声明底栏 56（同时确认 80 不被误用）。

### 需求 2 · 文字大小适中（建立合理字阶）

| 项目 | 现状 | 目标（适中字阶） | 证据 |
|---|---|---|---|
| 字阶跨度 | `12 / 14 / 16 / 20 / 24 / 32 / 40 dp`（7 档，跨度到 40 偏大） | `display 28 / headline 22 / title 18 / body-lg 16 / body-md 14 / label 13 / caption 12`，行高 1.2–1.5×，字重 400/500/600 | `DESIGN_LANGUAGE.md:122` 字号阶梯；`Theme.kt:35-43` `AppTypography` |

**诊断**：
- 现有最大档 `40dp`（displayLarge）对工具类 App 偏大、易显「可爱 iOS 标题感」；建议收敛到 **28dp** 封顶，更克制专业。
- 缺少 `13px` 的 `label` 档（底部 tab 标签、辅助说明），当前用 `labelMedium=12` 兜底，层级不够；补 `label 13/18/500` 更适中发现项密度。
- 行高需明确：正文 1.5×（16/24）、标题 1.2–1.3×（28/34、22/28），避免原「标题 1.2× / 正文 1.5×」描述过粗。

**结论**：采用上方「目标字阶」七档（已在 `design-tokens.json → typography` 落定），弃用 32/40 两档；标题字重统一 600，正文 400，标签 500。字族从圆体（Nunito/Quicksand）改为**中性无衬线**（Inter / 系统黑体），这是「从可爱到专业」的关键一步。

### 需求 3 · 整体黑白为主、蓝为点缀（头号结论：换色板）

> **这是本次审计最关键的一条：现有设计与用户方向根本冲突，必须整体换色板，不是局部调整。**

**冲突证据链（铁证）**：

1. `DESIGN_LANGUAGE.md:11`（§1 铁律 1）：
   > 「**色彩单调但温暖**：全界面只用**一个主色**（珊瑚粉），其余皆暖中性灰；禁止多色拼贴。」
2. `DESIGN_LANGUAGE.md:32`（§2.1）：`--primary = OKLCH(0.78 0.10 25)` —— 珊瑚粉（色相 25 = 暖红粉）。
3. `Color.kt:16`：`md_primary_light = Color(0xFFF19E97)` —— 珊瑚粉的 sRGB 实值，`Theme.kt:52` 直接接入 `primary`。
4. 暗色同理：`Color.kt:31` `md_primary_dark = Color(0xFFFFABA3)`（亮珊瑚粉）。

而用户明确要求「**黑白为主 + 蓝点缀**」。珊瑚粉的 OKLCH 彩度 0.10、色相 25（暖红），与蓝（色相 ~258）在色相环上几乎相对，**无法共存于同一主色位**。因此：

- [缺失] 不能「把珊瑚粉调成蓝」——那是改色相，等于推翻原色彩铁律；
- [齐备] 必须**整体换色板**：中性走黑白色阶，主色位替换为蓝 `#2563EB` 家族。

**为何选 `#2563EB`（蓝 600）作为点缀主色**：
- **现代、干净、专业**：Blue-600 是当下主流工具/系统 UI（Material、iOS 系统蓝、Stripe、Linear 系）的高可信度色，天然传达「工具/效率」而非「可爱/消费」；
- **高对比、可读性强**：在白底 `#FFFFFF` 上 `#2563EB` 对比度 ≈ 4.6:1（AA 正文临界），配白字按钮对比度 ≈ 4.5:1+，可达 AA；暗色下提亮为 `#5B8DEF`（对比度更高）；
- **Android / Material 友好**：直接映射 M3 `primary` 色槽，无需自定义色彩学；蓝色在系统导航/链接/选中态上有强语义一致性（用户一眼懂「蓝 = 可点/选中」）；
- **克制**：蓝仅作点缀（主色占比 < 15%），大面积仍是中性黑白灰，契合「黑白为主」。

**锁定色板（主理人已定，设计层严格采用，全量见 `design-tokens.json`）**：
- 中性：亮 `--bg #F6F7F9 / --surface #FFFFFF / --surface-2 #F0F1F3 / --on-surface #14171A / --on-surface-variant #5B616E / --outline #E2E5E9 / --outline-variant #EDEFF2`；暗对应 `#0E0F11 / #16181B / #1E2125 / #F2F4F6 / #9BA1A8 / #2A2E33 / #23272C`。
- 蓝刻度：50 `#EFF4FF` → 900 `#15346F`，主色亮 `#2563EB` / 暗 `#5B8DEF`，容器 `primaryContainer` 亮 `#E6EFFF` / 暗 `#15315E`。
- 语义：success `#16A34A`(暗`#22C55E`) / warning `#D97706`(暗`#F59E0B`) / error `#DC2626`(暗`#F87171`) / info 复用 primary 蓝。

**结论**：`DESIGN_LANGUAGE.md` §1 铁律与 §2 色板需整体改写为「黑白中性 + 蓝点缀」；`Color.kt` 全部 primary/primaryContainer/onPrimary 系列替换为蓝家族。这是与架构师锁定的色板**完全一致**的唯一正确路径。

### 需求 4 · 令牌覆盖所有卡片、组件（不要遗漏）

**现状覆盖度审计**：

| 令牌类别 | 现状 | 是否齐备 | 证据 |
|---|---|---|---|
| 颜色原语 | `Color.kt` 定义了 neutral/primary/语义 | [注意] 值需换（珊瑚粉→蓝），且**缺 outline-variant、缺蓝刻度 50–900 全档** | `Color.kt:10-37` |
| 间距原语 | `Spacing.kt` + `MmaDesign.SpacingScale` 3/6/9/12/18/24/36 | [齐备] 齐备（与锁定一致） | `Spacing.kt`、`MmaDesign.kt:17-38` |
| 圆角原语 | `Theme.kt: AppShapes` 8/16/24/999 | [注意] **值不对齐**：锁定为 6/12/16/20/999，当前是 8/16/24/999 | `Theme.kt:22-28`、`DESIGN_LANGUAGE.md:75-78` |
| 字型原语 | `Theme.kt: AppTypography` | [注意] 字号需收敛、字族需换中性 | `Theme.kt:35-43` |
| **阴影/抬升令牌** | **仅 `DESIGN_LANGUAGE.md:145-146` 以散文 rgba 出现，代码中无 `ElevationToken` 对象** | [缺失] **缺失** | `DESIGN_LANGUAGE.md:145-146`；`MmaDesign.kt` 无 elevation 字段 |
| **组件级语义令牌** | **无**：card / button / input / chip / badge / dialog / topBar / bottomBar 等均未令牌化 | [缺失] **缺失** | 全仓库无 `ComponentToken`；组件各自硬编码尺寸/颜色 |

**缺令牌导致的设计遗漏风险**（即「不要设计遗漏」的具体落点）：
- 卡片（Card）：背景/圆角/阴影/内边距无统一令牌 → 不同页面卡片观感漂移；
- 按钮（Filled/Text/Tonal）：高度(44)、圆角(pill)、主色引用无令牌；
- 输入框（TextField）：聚焦态蓝色描边环、占位色无令牌；
- 顶/底栏：高度（52/56）、选中蓝、指示块蓝容器无令牌（见需求 1）；
- Chip / 状态徽标（success/error）/ 对话框 / FAB：均散落硬编码。

**应补齐的组件令牌清单**（已落定到 `design-tokens.json → component`，供架构师直接消费）：
1. `topBar` — height/bg/borderBottom/titleStyle
2. `bottomBar` — height/bg/borderTop/selectedColor/indicator
3. `card` — bg/radius/elevation/padding/border
4. `cardGroup` — 分组列表卡（用 divider 替代多卡堆叠）
5. `input` — bg/border/radius/focusBorder/placeholder/text
6. `button.filled` / `button.text` / `button.tonal`
7. `chip` — bg/fg/radius/height
8. `badge.success` / `badge.error` / `badge.neutral`
9. `dialog` — bg/radius/elevation/padding/titleStyle/bodyStyle
10. `fab` — bg/fg/radius/size

**结论**：在既有「颜色/间距/圆角/字型」四原语之上，**必须新增（a）`elevation` 阴影令牌、（b）上述 10 类组件级语义令牌**，方能实现「令牌覆盖所有卡片、组件、无遗漏」。这些值已写入 `design-tokens.json`，可作为工程师新增 `ElevationToken` / `ComponentToken` 数据类的蓝图。

## 2. 整体风格方向建议

| 维度 | 旧（可爱简约 iOS） | 新方向（本审计建议） | 理由 |
|---|---|---|---|
| 主色 | 珊瑚粉 `#F19E97`（暖红粉） | 蓝 `#2563EB`（点缀 <15%） | 用户硬需求；蓝更专业可信 |
| 基调 | 暖中性 + 圆体 + 柔光 | **黑白中性 + 中性无衬线 + 干净阴影** | 从「可爱」转向「工具/效率」 |
| 圆角 | 大圆角 16/24 + 胶囊 | 收敛 6/12/16/20 + 胶囊(按钮) | 减少「果冻感」，更利落 |
| 阴影 | 大模糊低透柔光（iOS 柔） | 轻量 1–2 层低透阴影（elevation-1/2） | 干净、专业、不浮夸 |
| 留白 | 低密度、强呼吸 | 适度留白（沿用紧凑间距档） | 保持信息密度合理 |
| 动效 | 弹簧回弹、慢节奏 | **收敛**：保留 150–300ms 微交互，去掉过度回弹 | 专业界面不宜「弹」 |

**一句话风格**：黑白做底、蓝色点睛、圆角利落、阴影克制、字阶适中——一个「看起来不像 AI 模板、也不像可爱 App」的干净工具界面。

## 5. 补充审计：主题色链路遗漏（2026-10-28 晚，用户验收发现）

> 用户反馈"创建项目页面还有令牌是旧配色"。排查确认：§3 实施路线只覆盖了
> `ui/theme` 与组件层，**没有审计"主题色数据链路"**——旧珊瑚粉以"项目默认
> 主题色"的身份活在数据层，UI 重构后新建项目依旧默认珊瑚粉。

### 5.1 遗漏清单（已全部修复）

| 层 | 位置 | 问题 | 修复 |
|---|---|---|---|
| 数据层默认值 | `ProjectDefaults.DEFAULT_THEME_COLOR` | `0xFFE39E97` 珊瑚粉，新建/迁移兜底全继承 | 改 `0xFF2563EB`（设计语言主色蓝） |
| 编辑页色板 | `WebSettingsTab.THEME_PRESETS[0]` | 珊瑚粉且标注"（默认）"，整板为旧马卡龙系 | 首项改蓝（默认），色板对齐设计语言语义色 |
| 测试固定值 | 15 个测试文件的 `themeColor` 输入与断言 | 硬编码珊瑚粉 | 统一 `0xFF2563EB`；迁移测试模拟历史数据行加 `// legacy-color` 豁免 |

### 5.2 漏网原因（门禁盲区，均已封堵）

1. **裸 ARGB 字面量**：`0xFFE39E97.toInt()` 不含 `Color(` 前缀，不匹配
   `COLOR_HEX_RE`；2. **扫描范围盲区**：令牌门禁只扫 `ui/` 包，`data/model`
   的默认值、ViewModel、测试源码均不在范围内；3. **审计方法盲区**：UI 审计
   只看"界面画了什么色"，没追"数据链路里存了什么色"。

### 5.3 防复发机制（不允许下次出现）

- `check_token_usage.py` 新增**检查项 5：废弃色黑名单**（`RETIRED_COLORS`）——
  扫描**全仓库** Kotlin 源码（主源码 + 测试，theme/ 不豁免），命中即失败；
  裸 ARGB 与带 alpha 前缀两种写法都拦；黑名单一次一除、永不摘除。
- 豁免标记 `// legacy-color <理由>` 仅限模拟历史数据的迁移测试，主源码禁用。
- **方法论沉淀**：今后任何色彩重构，审计范围必须包含「令牌定义层 + UI 消费层 +
  **数据默认值层** + 测试固定值层」四层，缺一不算审完。

5. **保存 loading**：顶栏保存按钮 saving 时显示 16dp 进度圈（白名单尺寸），防重复提交。
6. **UI 美化**：身份区改为「图标 + 应用图标说明两行」排版，替代裸 Row + TextButton。

### 6.3 技术决策（ADR 摘要）

- **图标存拷贝而非 content:// URI**：Photo Picker 授权 URI 跨重启不可靠，拷贝进
  应用私有目录保证列表/编辑/预览任意时刻可解码，且源图删除不影响项目。
- **扩展名统一 .png**：`validateIconRef` 对非 png 给警告；Android 解码按内容判型，
  扩展名仅服务校验友好。
- **解码异步 + 占位兜底**：首帧恒占位（与快照基线一致），文件可解码后换真图；
  `ProjectIconDecoder` 独立对象便于单测。
